## What changed

Roder 0.1.21 updates the local file-tool path resolver so Codex-style canonical paths work in the normal Roder tool surface. A path that starts with `user://` now resolves from the signed-in user's home directory, while `workspace://` resolves from the active workspace root. The same resolver is used by the read, list, search, image, write, edit, and multi-edit tools.

That means an agent can open a skill or project-local resource using the durable path it was given instead of treating the scheme as a literal directory name. For example, `user://.codex/skills/demo/SKILL.md` points at `$HOME/.codex/skills/demo/SKILL.md`, and `workspace://.agents/skills/review/SKILL.md` points at `.agents/skills/review/SKILL.md` inside the current repo.

## Why it matters

- Skills and tool instructions can pass stable canonical paths without first translating them to machine-specific absolute paths.
- Workspace-scoped resources stay explicit, which avoids confusing a project-relative file with a home-directory file.
- Models can use the same path form across `read_file`, `list_files`, `grep`, `glob`, `view_image`, and edit tools.
- Local and remote-runner turns get the same interpretation for home and workspace aliases, so a working prompt is less tied to one shell session.

## Using it

Ask Roder to inspect a canonical path directly:

```text
Read user://.codex/skills/review/SKILL.md and apply the relevant review rules.
```

For project-owned agent assets:

```text
Open workspace://.agents/skills/roadmap/SKILL.md before updating the roadmap item.
```

Relative paths, absolute paths, and `~/...` continue to work. The new aliases are most useful when a tool, skill, or automation wants to hand the model a location that should stay meaningful across workspaces and machines.
