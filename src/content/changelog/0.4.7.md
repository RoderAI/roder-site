## Use a Chat Completions endpoint with the Roder runtime

Custom inference providers can now set `protocol = "chat_completions"` to use Roder's native Rust transport. The adapter streams answers, assembles tool calls and returns approved tool results to the model through the normal runtime.

Configure an API root with `base_url`, reference the endpoint credential through `api_key_env`, and select the custom provider and model for the session. Roder appends `/chat/completions` to the API root; do not put the full completion path in `base_url`.

See [custom Chat Completions setup](/docs/providers/#custom-chat-completions) for a complete configuration example.

## Fit the request to the deployed backend

Optional `models` supplies explicit model IDs when `/models` discovery is unavailable. Set `context_window` to the server's deployed token limit, which may be smaller than the model's advertised maximum; Roder uses it for metadata and prompt budgeting.

An optional `tool_allowlist` reduces the tool schemas sent to this provider. It is useful for small-context endpoints, but it is not an execution permission boundary: normal tool approval and access policies still apply. These settings are scoped to the configured provider and do not switch the main model or alter other providers.

## Existing Responses providers keep their defaults

Custom providers still use Responses when `protocol` is omitted. Their existing defaults and capability settings are unchanged.

Chat Completions compatibility depends on the endpoint's streaming and tool-call support. This custom adapter does not advertise image input, prompt caching or provider-native tool search; configuring it does not turn a Chat Completions backend into a Responses backend.
